# 代码优化实施计划

## 目标

在不改变数仓口径、生成产物、CLI 参数和部署安全护栏的前提下，逐步提升项目的可维护性、回归安全和运行效率。

当前优先事项是降低大型编排模块的修改风险，而不是先重写已有性能路径。MAPPING Excel 解析已经有 `python-calamine` 快速路径和文件级缓存；后续性能优化应以实际 profiling 结果为依据。

## 范围与原则

- 优先改造 `tools/dw-pipeline.py`，再评估生成器和 DS 部署模块。
- 每次只改一个职责域；先补行为测试，再搬移代码。
- 保持现有 CLI 入口、参数、退出码、阶段顺序和默认 dry-run 行为。
- 不更改 ODS/DWD/DWS 命名、分区、字段或血缘口径。
- 不允许普通生成流程覆盖 `MASTER` 甲方脚本和人工血缘。
- 不覆盖已修复的 DWS 脚本；不把真实 DS/Hive 调用放入普通单元测试。
- 缓存只负责提速，不能影响正确性；缓存不可用时仍须能够正常解析。
- 不将外部交付文档、凭据或环境专属数据加入测试夹具。

## 阶段 1：建立基线与行为契约

### 工作项

1. 选取代表性输入，覆盖 ODS 调研、普通 DWD MAPPING、DWS MAPPING 和 `MASTER` 特殊保护路径。
2. 记录各阶段耗时：Excel 解析、DDL/ETL 生成、血缘/依赖配置、校验；区分缓存冷读与命中。
3. 建立产物比较基线，重点比较 DDL 表/字段、ETL 脚本内容、血缘记录和依赖配置，而不只比较文件数。
   基线产物放在 `tools/.dx-tmp/`（已 gitignore），**不入库**；比对写成可选脚本
   （如 `tools/tests/baseline_compare.py`），默认 `skip`，仅当设置 `DW_BASELINE=1` 时执行。
   ★ CI 只有 Ubuntu + `requirements.txt`，**没有 `/mnt/d`**，拿不到甲方交付文档
   ⇒ 真实交付物比对只能在本地跑，CI 只跑合成夹具。
4. 检查并补充关键行为测试：
   - dry-run 不写文件、不删除文件、不连接或修改 DS；
   - 子步骤失败时后续阶段不继续；
   - `--apply` 与其他选项正确传入子命令；
   - `MASTER` 保护规则有效；
   - DWS 修复标记能阻止甲方原文覆盖。
5. 使用最小合成 Excel 或脱敏夹具；测试结果写入临时目录。

### 验收标准

- 有一组可重复运行的基线测试和产物比较方法。
- 上述关键行为均有自动化测试覆盖。
- 基线记录不包含凭据或外部交付数据。

## 阶段 2：统一开发、测试和 CI 说明

### 工作项

1. **修正 README 的失效指令**（不只是措辞对齐）：`README.md` 目前要求用仓库内
   `.venv\Scripts\python.exe`，但该虚拟环境已不存在；`AGENTS.md` 明确 Windows 原生
   无 Python、统一在 WSL 里用 `python3`。README 应删除 Windows venv 段落，改为 WSL 命令。
2. 明确依赖安装与测试命令，确保本地和 CI 使用相同的依赖约束。
3. 整理本地检查顺序：单测、Python 编译、仓库 shell 语法检查；如不同环境不支持某项检查，说明适用条件。

### 验收标准

- 按文档在项目支持的环境中能够完成安装和测试。
- README、`AGENTS.md` 和 CI 对环境、依赖及命令的说明一致。

## 阶段 3：拆分 `tools/dw-pipeline.py`

### 工作项

1. 保留 `tools/dw-pipeline.py` 作为兼容 CLI 入口，先不改变命令名称、参数或默认行为。
2. 先抽出职责明确、较少副作用的代码，再迁移编排逻辑。新包命名为 `tools/dws/`
   （与既有 `tools/dwd/` 对称；**不要用 `tools/pipeline/`**，否则两个包职责重叠、
   命名难以区分）。可按以下方向组织：
   - `tools/dws/scripts.py`：生成、搬移与同步脚本；
   - `tools/dws/ddl.py`：DDL 清洗、写入和来源比对；
   - `tools/dws/lineage.py`：血缘与依赖配置；
   - `tools/dws/deploy.py`：DS 工作流操作；
   - `tools/dws/verify.py`：本地和 DS 校验；
   - `tools/dws/process.py`：子进程执行、超时与输出处理。
   ★ 搬迁前先产出「函数 → 模块」映射表并评审：`verify_ddl_after_write`、`parse_jf_ddl`、
     `dws_table_sys_map` 等被 ddl 与 verify 共用的函数必须先定归属，否则会拆出循环依赖。
3. 按“纯函数/本地文件操作 → 子进程编排 → DS 外部操作”的顺序迁移，避免一次性移动所有逻辑。
4. 检查现有测试对入口模块的动态加载和函数直接调用；迁移测试到新模块，必要时在入口保留兼容导出。
5. 每次迁移一个职责域后，对照基线验证生成结果和命令行为。

### 验收标准

- 既有子命令的帮助、参数、默认值、执行顺序和退出行为不变。
- 代表性输入的产物比较通过。
- dry-run 不产生副作用；失败即中止行为得到回归测试保护。
- 入口模块仅保留参数解析、命令分派和必要兼容层。

## 阶段 4：拆分生成器与部署模块

### 工作项

1. **顺序：先生成器，最后才是会写 DS 的模块。** `tools/generator/base.py` 是纯本地处理，
   先评估拆分；`tools/ds-deploy/ds-deploy-dwd-workflow.py` 会**写 DS**，风险最高，
   放到最后单独立项，且搬迁前必须先有 mock 化的请求参数基线。
2. 对 `tools/generator/base.py` 按 DDL 构建、ETL SQL 生成、JOIN/子查询处理等职责评估拆分。
3. `tools/dwd/generation.py` **仅在出现具体维护痛点时**再拆：它刚从 2193 行单体中拆出
   （现约 1141 行），没有 profiling 或维护证据前再拆属于过度设计（YAGNI）。
4. 只有在行为确实一致时才提取共享逻辑；不要合并有不同业务口径的命名、系统字段、分区或工作流规则。
5. 外部 DS/Hive 行为使用 mock、临时目录或可控测试替身验证，单元测试不得误连生产环境。

### 验收标准

- 新模块职责单一、依赖方向清晰且可独立测试。
- 生成器输出、DS 请求参数和失败处理与基线一致。
- 不为单纯减少文件行数而拆分模块。

## 阶段 5：基于测量结果进行性能优化

### 工作项

1. 根据阶段 1 的数据定位主要耗时；没有可重复的瓶颈证据时，不改性能实现。
2. 若瓶颈在 Excel 读取，检查 calamine 快速路径、缓存命中率，以及是否有入口绕过共享读取逻辑。
3. 若瓶颈在重复扫描，在单次管线运行内考虑复用文件清单或解析结果；保持缓存指纹、失效和回退策略。
4. 若瓶颈在子进程或 DS 请求，分别测量本地处理、进程启动和网络等待后再决定是否合并调用或并发化。
5. 每项优化都比较优化前后的冷读/热读时间，并执行产物一致性验证。

### 验收标准

- 有可复现的优化前后数据和明确收益。
- 产物比较通过，缓存禁用或失效时仍能正确运行。
- 错误不会被吞掉，超时和外部失败仍能明确报告。

## 阶段 6：分步验证与发布

每个职责域独立完成并验证后再进入下一项：

1. 运行相关单测和全量单测。
2. 运行 Python 编译检查和仓库 shell 语法检查。
3. 对代表性输入运行生成流程并比较产物。
4. 先运行 dry-run，审阅文件变更清单和 DS 操作计划。
5. 只有确认计划无误后，才由操作者显式执行 `--apply` 或连接 DS 验证。

### 最终验收标准

- 全量单测、编译检查和适用的 shell 语法检查通过。
- 代表性产物与基线一致，或每项有意差异都有明确说明和针对性测试。
- 所有写入及 DS 操作仍受显式确认/`--apply` 控制。
- `MASTER` 和 DWS 基线保护规则均通过回归测试。

## 建议执行顺序

1. 阶段 1：建立基线与行为契约。
2. 阶段 2：统一运行和测试说明。
3. 阶段 3：拆分 `dw-pipeline.py`。
4. 阶段 4：先拆生成器；DS 部署模块最后单独立项；`tools/dwd/generation.py` 暂不拆。
5. 阶段 5：仅优化实测瓶颈。
6. 阶段 6：按职责域逐步验收和发布。

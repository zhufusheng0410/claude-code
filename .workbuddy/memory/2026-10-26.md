## DWS 第二波：跨零点死锁 + 两处结构性缺陷（2026-10-27 00:00–00:30）
**① `dep_*` 依赖节点跨零点必死锁（重要，影响所有 DWS 自动调度）**
DWS 工作流里每个真实 SHELL 任务前挂了一个 `DEPENDENT` 节点 `dep_X`，图是
`dep_AST → SHELL_AST → dep_EQUI → SHELL_EQUI → …`。其依赖参数为
`dependentType=DEPENDENT_ON_TASK, cycle=day, dateValue=today`，即「等今天这个工作流的
某个已完成实例里的 X 成功」。`t_ds_workflow_instance.schedule_time` 为 NULL（手工触发），
DS 按 start_time 落在今天的窗口去找，**排除当前实例**。
- 23:31 跑 1474 时窗口里有 1469~1477 ⇒ 立刻拿到成功结果，dep 秒过；
- 00:01 跑 1478 时 2026-10-27 当天还没有更早实例 ⇒ 7 个 dep 节点全部 RUNNING 空等，
  而 SHELL 任务排在 dep 之后 ⇒ 永久挂起（master 日志刷
  `Wait for the dependent workflow to complete ... workflowInstanceId: 1478`）。
**结论：DWS 三个工作流在 00:00~当天首次成功之间无法运行。** 根治要把 `dateValue` 改成
`yesterday`（或改用 previous-cycle 语义），否则任何每日定时跑批都会挂。
临时规避：当晚先跑一次成功实例，或临时把这些 dep 节点停用。

- `dws_cust_hold_detail_ptd_tmp` 甲方32/Hive33：缺 `LD_TIME`，多重复列 `INCL_UNP_YIEL_SHARE_2` + `COL_X33`
- `dws_tran_acct_info_tmp` 甲方23/Hive33：多 10 个 `COL_X24..COL_X33`
按甲方 DDL 重建（`tools/ds-deploy/_rebuild_dws_tmp.sql`，备份 `_backup_dws_tmp_20261027/`）后归零。
**`dws_prod_scr_pl_detail_ptd` 不要动**：甲方 DDL 只写 23 列，但脚本真用 50 列 ⇒ 是甲方 DDL 不全，Hive 现状正确。

**② Hive 4.2 本环境 `CREATE TABLE` 默认建成 EXTERNAL**
建 managed 表要补 `ALTER TABLE x SET TBLPROPERTIES ("EXTERNAL"="FALSE")`。
反过来，脚本里 `TRUNCATE TABLE` 只对 managed 表有效，建成 EXTERNAL 会报
`Error 10146 Cannot truncate non-managed table`（ACCT_INFO_TMP 踩过）。

**③ 分区列会被计入 INSERT 目标列（Error 10044 的真正来源）**
三张 scratch TMP（`dws_tran_acct_info_tmp` 23、`dws_tran_acct_open_btch_pfd_tmp` 27、
`dws_cust_fst_tran_btch_pfd_tmp` 17）甲方 DDL 都声明了 `PARTITIONED BY(P_DT)`，但甲方 ETL 对它们
只做 `TRUNCATE` + `INSERT`（**不带 PARTITION 子句**），且从不按 p_dt 读写。Hive 4.2 会把分区列
算进 INSERT 目标列 ⇒ 表 N+1 列 / 查询 N 列。
**最终处置：把这 3 张建成「非分区 + managed」表**（`_rebuild_dws_scratch_tmp.sql`），
一处 DDL 解决全部错位，且不用改甲方 SQL。（曾给单条 INSERT 补 PARTITION 子句，但单文件内
有 8+ 处同类 INSERT，已全部回退。）

**④ `dep_*` 依赖跨零点死锁的根治**：dateValue `today` → `yesterday`
工具 `tools/.dx-tmp/_fix_dws_dep_datevalue.py`（读工作流定义→改 DEPENDENT.taskParams.dependence
.dependTaskList[].dependItemList[].dateValue→OFFLINE→PUT→ONLINE，复用 ds_client）。
三个 DWS 工作流共 **24 个 DEPENDENT 任务 / 120 条依赖项**全部改为 `yesterday`，库内已无 `today` 残留。
只改 dateValue、cycle 仍为 day ⇒ 语义变成「依赖上一业务日实例」，符合每日跑批。

## DWS 第四波：dep 守卫的真相 —— DS 3.4.2 没有「软依赖」（2026-10-27 00:45）

**踩坑链条**：dateValue 改 `yesterday` 后，10-27 00:33 的 1479、00:35 的 1480 仍然 8 个 dep 全
FAILURE（0~1 秒内立刻失败，连 SHELL 任务都没创建）。读 1480/18538 日志发现运行时参数里是
`"failurePolicy" : null` —— 我落的 `DEPENDENT_FAILURE_CONTINUE` 被反序列化成了 null。

**真相**：查容器内前端资源确认 DS **3.4.2 只认两个值**
```bash
docker exec dolphinscheduler-master sh -c \
 'grep -rho "DEPENDENT_FAILURE[A-Z_]*" /opt/dolphinscheduler/ui/ | sort | uniq -c'
# DEPENDENT_FAILURE_FAILURE / DEPENDENT_FAILURE_WAITING
```
**3.4.2 根本没有「失败继续」**。`DEPENDENT_FAILURE_CONTINUE` 是 2.x 的枚举，写进去静默变 null →
退回默认 FAILURE。所以「昨天失败则今天也放行」在 3.4.2 里用 dep 节点无法表达。

**关键观察**：依赖图实际是 `0 -> dep_X -> SHELL_X`，24 个 dep 全是**纯根节点**，彼此不串联，
本质只做「防同一工作流并发」。而三个工作流 `execution_type=1`（**SERIAL_WAIT**，DS 原生串行
等待）已经把这件事保证掉了 ⇒ dep_* 既冗余又是坏的。

**处置**：`tools/.dx-tmp/_drop_dws_dep.py`（--apply）删掉 24 个 dep_* 任务，把其下游 SHELL 提成根
节点（`preTaskCode=0`），其余不变；备份在 `tools/ds-deploy/_bak_dws_dep/*.json`。
结果：HSFA 14→7、O32 18→9、ZTA 16→8 个任务，dep=0、roots=任务数。

**ZTA 实测（实例 1481，params 1025/1025）**：8/8 SUCCESS，且用新增的
`tools/.dx-tmp/_verify_dws_run.py` 按日志核验 = **35 个真实 Tez 作业 / 35 次分区写入 / 0 报错**。
`dwsxday` 下 p_dt=20261025 分区共 22 个已落盘。

## 另一个澄清：dws_prod_scr_pl_detail_ptd 不是甲方脚本缺陷

之前判「甲方 DDL 只有 23 列、脚本用 50 列 ⇒ 甲方漏列」是**我的解析器错**（在

`tools/.dx-tmp/verify-<WF>-<inst>.json`。DS 记 SUCCESS 一律不可信，只认这个。

## DWS 第五波：并发超预算 → AM 被杀 → 假成功的闭环（2026-10-27 01:15）

**现象**：HSFA（实例 1482）7 个任务 00:43 起跑，5 个卡在 `VERTICES: 00/00 0%` 超 900s。
另 2 个先成功。杀掉 beeline 后 7/7 变 SUCCESS —— 又一次假成功（shell 尾命令 `done` 退出码 0）。

**根因（看容器名就看出来）**：`container_e75_..._0018_**02**_000001` = AM 的**第 2 次尝试**。
YARN 预算只有 **2048MB**（`yarn.nodemanager.resource.memory-mb`），
`tez.am.resource.memory.mb=256` + `tez.task.resource.memory.mb=256`（tez-site.xml 于 2026-10-23 下调）
⇒ 一个会话 512MB ⇒ **最多 4 个并发会话**。HSFA 7 个任务全成根节点一口气起 7 个 ⇒ 超卖
⇒ AM 被 YARN 杀掉重启 ⇒ 会话里的 DAG 丢失 ⇒ 客户端永远打印 `00/00 0%`（不是慢，是死）。
AM 重启后会 `RecoveryParser` 恢复上一个 DAG 并打印 `In Session mode. Waiting for DAG over RPC`，
很容易误读成"在排队"。

**处置**：`tools/.dx-tmp/_set_dws_lanes.py --lanes 2 --apply`
把三个工作流的任务按原顺序**轮转分到 2 条泳道**，道内串成链（`0 -> t0 -> t1 -> ...`），
并发钉死在 2（2×512=1024MB，给泄漏 AM 留 1GB 余量）。
- HSFA 2 道：道1 AST_INFO→SALE_DATA→SCR_PL→SUM_INFO；道2 EQUI→SCR_HLDP→SCR_TRAN
- O32 2 道各 5/4 个；ZTA 2 道各 4/4 个

**三个工作流全绿（2026-10-27 01:03~01:14，均约 3.5 分钟）**
| 工作流 | 实例 | DS | 真实作业 | 写分区 | 报错 |
|---|---|---|---|---|---|
| DWS_HSFA | 1483 | 7/7 | 7 | 7 | 0 |
| DWS_O32  | 1484 | 9/9 | 14 | 14 | 0 |
| DWS_ZTA  | 1485 | 8/8 | 35 | 35 | 0 |

`dwsxday` 下 `p_dt=20261025` 分区 **22 张表 / 22 个分区**全部落盘。
ZTA 从「8 并行」改「2 泳道」后真实作业数仍为 35，说明结果与并发方式无关，可复现。

**运维口诀**：跑 DWS 前先 `docker exec nodemanager1 pkill -9 -f DAGAppMaster`；
单看 `VERTICES: 00/00` 就是在等死，不是慢。
